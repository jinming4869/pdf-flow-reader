# PoC 结果

测试日期：2026-07-31。性能数据来自同一台 Apple Silicon 测试机，仅用于方案间相对比较。

## 结论

方案 A 的核心架构可行：Misaki 能为中日文产生真实音素，Kokoro ONNX 能在持久 child process 中离线、实时以下合成，父进程也能真正终止进行中的推理。日文路径已经达到进入正式集成前的技术门槛；中文需在 v1.1 音色与 v1.0 连续速度之间完成一次试听选择。

## 功能证据

- `12 passed`：语言归一化、资源门槛、v1.1 中文分数速度保护、NDJSON health/error/shutdown 契约。
- 实际 worker：中、日文各生成一个 24 kHz PCM WAV，未知音素均为 0。
- 硬取消：先完成中文预热，再发起长推理并在 50 ms 后终止 child；`cancelled=true`、`outputCreated=false`。
- 离线：将 HTTP/HTTPS/ALL proxy 指向不可达端口后，中、日文仍成功合成。
- 路径兼容：含中文工程路径下的 eSpeak 崩溃，已通过 child 内 ASCII shadow path 修复。

## 速度结果

日文 v1.0 int8 正常支持连续速度：同一句从 1.0x 的 3.947 秒缩短到 1.85x 的 1.792 秒，最慢一档 RTF 0.585，最快一档 RTF 0.794。

中文 v1.1 ONNX 的 `speed` 输入是 `tensor(int32)`；上游开放问题 `thewh1teagle/kokoro-onnx#155` 已确认分数速度被截断。1.0x 为 3.584 秒，2.0x 为 1.813 秒，但 1.25/1.5/1.85 都不能真实表达。PoC 现已对这些值显式报错，不再静默伪装成功。

中文 v1.0 int8 + legacy Misaki 对照则可连续变速：

| 请求速度 | 音频秒数 | RTF |
|---:|---:|---:|
| 1.0 | 7.403 | 0.527 |
| 1.25 | 6.443 | 0.588 |
| 1.5 | 4.523 | 0.592 |
| 1.85 | 3.968 | 0.581 |

## 产品结论

1. 中文正式集成采用 v1.0 `zf_xiaobei`，与日文共用 v1.0 int8：模型更小、速度连续、维护边界更简单。
2. v1.1 `zf_001` 保留为历史对照，不进入正式资源；其分数速度问题需要新的 ONNX 导出或高质量 time-stretch 才能解决。
3. 日文采用 v1.0 int8 + `JAG2P(version="pyopenjtalk")`。

## 发布前风险

- PoC 总本地占用约 933 MiB（模型约 508 MiB、环境约 425 MiB）；正式包需裁剪无关 Python 依赖并按语言拆包。
- `phonemizer-fork` 为 GPL-3.0-or-later。MIT 主应用如何与独立 Python child 一同分发，需要单独做许可证方案；也可通过直接 ONNX tokenization 和复用现有英语链来移除 phonemizer/eSpeak。
- RTF 和音素覆盖只能证明运行正确，不能单独证明发音自然度。
